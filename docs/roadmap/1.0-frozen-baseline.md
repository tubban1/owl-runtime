# OWL Runtime 1.0 Frozen Baseline

Status: **FROZEN TARGET**  
Target release: **1.0.0**  
Current release-candidate line: **1.0.0-rc.x**  
Freeze date: **2026-09-28**

This document is the normative feature boundary for OWL Runtime 1.0. It incorporates the final Owl Lab design/code audit and a real-world operational review of the legacy AgentOS/Computer MCP state stores without reopening the 1.0 feature surface.

## 1. What 1.0 is

OWL Runtime 1.0 is a **reliable local execution kernel** for AI clients and products.

It owns:

- RuntimeClient / HTTP execution boundary;
- Primitive and Skill execution contracts;
- durable Task / Schedule / Loop state;
- managed Process lifecycle and ownership;
- Resource Arbiter and workspace leases;
- request cancellation;
- Observation and Verification;
- Approval enforcement;
- Health and Diagnostics;
- ExecutionTarget contract;
- versioned state / crash recovery / upgrade and rollback mechanics.

It does not own a general-purpose Planner, Worker product UX, MCP product behavior, business-specific orchestration, enterprise control plane, or autonomous kernel self-modification.

## 2. Frozen architectural laws

The following Owl Lab lessons are accepted into 1.0 because they are execution invariants, not new features.

### 2.1 Physical truth beats caller belief

Where Runtime can observe physical execution state, it must not report success based only on caller/planner expectation.

### 2.2 Observe → Act → Verify

Provider return without an exception is not proof of business success.

Machine-verifiable side effects should be verified. Semantic side effects require an explicit postcondition. When evidence is insufficient, the result is `uncertain`, not success.

### 2.3 Fail closed on sensor/verification loss

A failed screenshot, inaccessible UI tree, disconnected provider, or unavailable verifier must never be converted to implicit success.

### 2.4 Durable identity is not transport identity

Transport sessions may reconnect, rotate, disappear, or be recreated. Durable Task, Process, Schedule, transaction and logical Runtime ownership must survive transport churn.

### 2.5 Cancellation is an execution boundary

Cancellation must propagate to live work where possible, and **a request cancelled while waiting for a resource must be removed from the pending resource queue**. A cancelled request must never receive the resource later and execute as a late side effect.

### 2.6 Stable semantics above replaceable providers

Primitive/public semantics remain stable even when browser, desktop helper, shell, filesystem or future provider implementations change.

### 2.7 No silent target/provider fallback for side effects

Unavailable execution targets fail closed. Runtime may not silently move a consequential action from one execution environment to another.

### 2.8 Lifecycle closure

Tasks, processes, leases, approvals and other durable resources must have observable terminal/reconciliation paths.

## 3. Real-world operational evidence

The 1.0 freeze was informed by an audit of the existing production state under the legacy AgentOS / Computer MCP installation.

No secrets, credentials, raw command payloads or user data are part of the Runtime release evidence.

### 3.1 macOS permission churn was real

The historical Computer MCP audit contained **33 macOS filesystem permission failures**.

The current production packaging has already moved Accessibility and Screen Recording authority to a stable helper application identity at a fixed application path. Current provider health reported both Accessibility and Screen Recording as granted.

**1.0 consequence:** Runtime must preserve the architectural rule that OS-granted permissions belong to a stable host/helper identity. Patch/minor code releases must not require a new privileged executable identity merely because the JavaScript/Runtime release directory changed.

This is primarily a packaging/host invariant, not a reason to add a new Runtime permission subsystem.

### 3.2 transport/session churn is normal, not exceptional

The legacy tunnel log showed:

- 1,699 distinct transport session IDs in the sampled log;
- 66 command-request root groups;
- 59 of those groups used more than one transport session;
- one command-request root was observed across as many as 154 transport session IDs.

At the time of audit the production runtime reported 7 active sessions but 671 known sessions retained in its session registry.

**1.0 consequence:** transport session identity must never be used as the sole durable owner of long-running work. This requirement is frozen.

### 3.3 resource contention was a common failure mode

The legacy audit contained at least **39 RESOURCE_WAIT_TIMEOUT-class errors** across shell/file operations, plus additional WORKSPACE_BUSY events.

OWL Runtime intentionally replaced short fixed resource wait failures with queued arbitration and explicit workspace ownership.

**1.0 consequence:** contention is a first-class state. Waiting must be observable and cancellable; stale session leases must be reclaimable; durable Task/Process ownership must remain explicit.

### 3.4 network/tunnel interruption is expected

The tunnel log contained multiple upstream/network warnings and at least 15 poll timeouts.

**1.0 consequence:** network or MCP disconnects must not corrupt Runtime state, leak ownership, or cause cancelled queued work to execute later.

### 3.5 long-running commands are common

Legacy production telemetry showed synchronous `execute_command` calls with very long wall times; current samples included a p95 around one minute and maxima around two minutes, with historical audit entries much longer.

**1.0 consequence:** long work must have a durable Process/Task path. Runtime correctness must not depend on one uninterrupted HTTP/MCP request staying open for the full external job duration.

This does **not** require adding a new long-wait Primitive to 1.0. The post-freeze managed-process Task wait work is reserved for 1.x.

### 3.6 persistent process state survives real usage

The audited legacy store contained 189 persistent process records; all were terminal at audit time, with a small number marked orphaned historically.

**1.0 consequence:** Process ownership, orphan detection, reclaim/control after reconnect, terminal reconciliation, and lease cleanup are release-critical behavior.

### 3.7 stale logical records exist in old systems

The legacy transaction store contained completed history plus two old records still marked active while no workspace lease was held.

This is evidence for stronger lifecycle reconciliation, but it is **not a 1.0 blocker** because an active transaction can intentionally outlive a lease and because OWL Runtime does not treat such a record as proof of current physical ownership.

Stale transaction classification/retention belongs to 1.x diagnostics/lifecycle work.

## 4. Owl Lab audit: what enters 1.0

Accepted as frozen behavior or redline:

- fail-closed verification;
- physical evidence over optimistic success;
- durable identity over transport identity;
- cancellation-aware execution;
- explicit resource ownership;
- stable provider-independent semantics;
- approval as enforceable authority transfer;
- no silent side-effect fallback;
- production self-protection;
- structured Health/Diagnostics rather than hidden degradation;
- trusted kernel does not autonomously rewrite itself.

## 5. Owl Lab audit: what does NOT enter 1.0

The following are valuable but would reopen the feature surface and therefore belong to 1.x or later:

- GroundedState;
- Governed Capability Manifest;
- RemediationReceipt;
- generalized Verification Plan / precondition + evidence + failure-policy contract;
- phase-aware capability inhibition;
- priority/preemptive scheduling;
- richer ArtifactRef/attachment ingestion;
- new App Adapter protocol;
- coordinate-frame visual grounding contract;
- autonomous Skill distillation;
- self-repair agent;
- sandbox/remote execution implementation.

## 6. 1.0 blocker fixed during final audit

The final operational audit found a cancellation correctness gap in the Resource Arbiter:

> a request cancelled while queued behind a conflicting resource could remain pending and later acquire the resource.

The 1.0 stabilization line must include the fix that removes a cancelled waiter atomically from the pending queue and proves that it can never be granted after cancellation.

This is a correctness fix, not a feature expansion.

### 6.1 Stable macOS permission host

The final packaging audit also found that the original OWL production installer still launched versioned `run.sh` / Node release paths directly. That did not fully satisfy the frozen requirement that Full Disk Access belong to a stable executable identity.

The 1.0 stabilization line therefore includes a fixed native host:

```text
~/Applications/OWL Runtime.app
bundle id: fan.fde.owl.runtime
```

The host is versioned and fingerprinted independently from Runtime code. Ordinary Runtime releases preserve the installed host binary; native-host replacement is explicit and separately reviewed.

This is a production identity/reliability correction, not a new Runtime execution capability.

### 6.2 Connected leases are never stolen because of idle time

Long-soak testing exposed an unsafe recovery heuristic: a still-connected session-only workspace lease could become reclaimable after an idle timeout, allowing a competing writer to enter the same workspace.

OWL Runtime 1.0 removes active-idle reclamation. Session-only ownership may be reclaimed after a known disconnect or Runtime-instance replacement, and otherwise ends through explicit release/handoff or its own TTL.

This is a concurrency correctness fix. When ownership is uncertain, 1.0 prefers a temporarily busy workspace over unsafe concurrent writes.

## 7. Explicitly deferred local work

Local commit `915ea9e` ("keep long process waits inside tasks") is **not part of 1.0**.

It contains useful 1.x work, including:

- `process.manage(wait)` as a persistent Task step;
- longer local process waits;
- background/headless browser default behavior;
- a complex Worker-style long-process benchmark.

It is preserved on a separate 1.x branch and must not be merged into the frozen 1.0 release solely for convenience.

## 8. 1.0 release gates

A build may be promoted to stable `1.0.0` only if all of the following are true:

1. full RC conformance passes on the exact release SHA;
2. cancellation while waiting for a Resource Arbiter conflict is proven to remove the waiter and prevent late execution;
3. RuntimeClient in-process and HTTP conformance pass;
4. clean tarball install works from a fresh consumer directory;
5. production daemon starts from the packaged artifact;
6. product-path dogfood covers Task, Process, Schedule, Health and Diagnostics;
7. Browser/Desktop verification remains fail-closed;
8. reconnect/process ownership tests pass;
9. workspace lease reclamation and no-leak checks pass;
10. production upgrade/rollback tests pass;
11. 2-hour real soak passes;
12. 6-hour real soak passes;
13. 24-hour real soak passes;
14. fresh-machine setup is verified;
15. macOS privileged helper/host identity survives a release update without unnecessary permission re-grant;
16. final Diagnostics report shows no non-terminal leaked Tasks, running orphaned managed processes, or workspace lease leaks attributable to the test.

No checkbox may be replaced by a shorter synthetic run.

## 9. Patch policy after 1.0.0

Allowed in `1.0.x`:

- security fixes;
- correctness fixes;
- cancellation/recovery fixes;
- data-loss prevention;
- state-schema compatibility fixes;
- ownership/isolation fixes;
- public-contract correctness fixes;
- measurable production reliability fixes that do not add a new public architecture surface.

Not allowed in `1.0.x`:

- new planner behavior;
- new public protocol families;
- sandbox/remote backends;
- new memory architecture;
- automatic Skill generation;
- new product orchestration;
- speculative feature expansion.

## 10. Consumer relationship at 1.0

```text
computer-mcp ─┐
              ├── RuntimeClient → OWL Runtime
owl-worker  ──┘
```

Computer MCP and OWL Worker do not need to wait for 1.x to continue product development. They should use the frozen 1.0 contract and submit explicit contract requests when repeated product evidence exposes a generic Runtime gap.

OWL Runtime 1.0 ends when reliable execution is proven. It does not end when every interesting Owl Lab idea has been implemented.
