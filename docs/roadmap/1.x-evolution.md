# OWL Runtime 1.x Evolution Plan

Status: **POST-1.0 EVOLUTION CONTRACT**  
Applies after stable `1.0.0`.

The goal of 1.x is not to make OWL Runtime larger. It is to make the execution kernel more grounded, more explainable, and easier for Computer MCP and OWL Worker to consume without duplicating Runtime logic.

## 1. Version discipline

### 1.0.x

Maintenance only:

- correctness;
- security;
- cancellation/recovery;
- state compatibility;
- ownership/isolation;
- public-contract correctness;
- measured production reliability fixes.

No new public architecture surface.

### 1.1

Maximum **three** new generic public protocol surfaces:

1. **GroundedState v1**
2. **RemediationReceipt v1**
3. **Governed Capability Manifest v1**

These are evidence-gated proposals, not automatic commitments.

### 1.2+

Additional protocol work may be considered only after the 1.1 surfaces are proven in real consumers.

## 2. GroundedState v1

Problem:

Planner/client belief can become stale between planning and execution.

Goal:

Expose a compact, execution-scoped truth token containing only facts material to the pending action.

Candidate fields:

- capturedAt;
- timezone/time anchor when relevant;
- ExecutionTarget;
- workspace identity/scope;
- provider health and required permissions;
- relevant active browser/page/app identity;
- ownership/lease state;
- provenance of each grounded fact.

Rules:

- no giant machine-state dump;
- facts must be fresh enough for the action;
- grounding is not business planning;
- consumer may request grounding, but Runtime owns physical truth.

Evidence trigger:

Repeated Worker/Computer MCP failures caused by stale environment assumptions.

## 3. RemediationReceipt v1

Problem:

Consumers currently see heterogeneous low-level failures and may duplicate error parsing/recovery logic.

Goal:

Normalize failures into a small execution language.

Candidate classes:

- `fatal`;
- `retriable`;
- `auth_required`;
- `permission_required`;
- `approval_required`;
- `conflict`;
- `ambiguous`;
- `uncertain_side_effect`;
- `needs_replan`.

Candidate receipt fields:

- class;
- reason;
- safeAutomaticAction;
- automaticReplayAllowed;
- evidence/observation reference;
- retryAfter / backoff hint;
- approval/permission requirement;
- provider/target;
- provenance.

Rules:

- deterministic recovery first;
- uncertain side effects never authorize blind replay;
- expensive recovery requires accumulated evidence;
- Runtime suggests the next safe execution move, not business intent.

## 4. Governed Capability Manifest v1

Problem:

A flat list of registered tools does not tell a Planner what is actually valid now.

Goal:

Evolve discovery from:

> what exists?

to:

> what is currently available, healthy, authorized, target-valid and appropriate for this consumer context?

Shaping pipeline:

```text
registered
→ available
→ healthy/integrity-valid
→ permission-valid
→ policy-valid
→ ExecutionTarget-valid
→ context/phase filtering
→ consumer-visible manifest
```

Candidate metadata:

- availability;
- health/integrity;
- supported operations;
- risk/side effects;
- approval requirement;
- idempotency/retry semantics;
- ExecutionTarget support;
- suppression/inhibition reason;
- provider affinity;
- contract version.

Rules:

- retrieve broadly, expose narrowly;
- visibility is governance, but visibility is not authorization;
- Runtime shapes valid capability facts;
- Planner still chooses business strategy.

## 5. Internal hardening that does not consume public protocol budget

The Owl Lab code audit found several valuable implementation ideas that should preferably strengthen existing internals rather than create new APIs.

### 5.1 Zero-trust control/data envelope

Separate Runtime control metadata from provider/business args.

Control plane examples:

- session/request identity;
- Task/Run identity;
- ExecutionTarget;
- cancellation;
- approval;
- verification policy;
- trace/provenance.

Data plane:

- action/provider arguments only.

Goal: prevent runtime metadata pollution and stabilize provider signatures.

### 5.2 type-preserving Task references

Exact references should preserve native values such as numbers, arrays and objects.

Do not silently stringify values at durable Task boundaries.

Any richer traversal syntax must remain deterministic and schema-validated.

### 5.3 failure-threshold escalation

Heavy remediation or repair should require repeated evidence or a strong invariant.

Suggested ladder:

```text
safe deterministic retry
→ reobserve
→ known provider recovery
→ needs_replan / attention
→ external repair workflow
```

No single transient failure should trigger architecture-changing repair.

### 5.4 capability health/integrity

Capability discovery should reuse Health/provider status and eventually expose integrity state through the governed manifest.

### 5.5 App Adapter role decomposition

Future complex app adapters should prefer:

```text
Adapter
├─ Locator / Resolver
├─ Executor
├─ Observer / Verifier
├─ Event Source / Watcher
└─ Protocol Gateway (optional)
```

Watcher emits events into durable Runtime orchestration; it should not own opaque infinite business loops.

### 5.6 visual coordinate provenance

Model-assisted visual localization should carry:

- source window identity;
- capture bounds;
- timestamp;
- coordinate frame;
- normalized target;
- global mapping receipt.

Never treat sensor failure as success.

### 5.7 evidence ledger

Benchmarks/soak/release evidence should remain machine-readable and tied to:

- Runtime version/SHA;
- scenario;
- attempts;
- recovery;
- duration;
- terminal status;
- duplicate side effects;
- leaked Task/Process/Lease state.

## 6. 1.x lifecycle and operations work

Real production state exposed several useful later improvements.

### 6.1 transaction lifecycle reconciliation

Legacy state contained old transactions still marked active after physical ownership had disappeared.

Potential 1.x work:

- stale/abandoned transaction classification;
- diagnostics signal;
- explicit reconcile/archive operation;
- retention policy;
- no automatic rollback based solely on age.

### 6.2 Process/Session retention

Large histories of terminal Process and Session records are normal under real use.

Potential work:

- configurable retention;
- compact/archive terminal records;
- preserve audit provenance;
- ensure compaction never affects live ownership.

### 6.3 cached health freshness

Cached health artifacts can become older than the live Runtime.

Potential work:

- `generatedAt`;
- Runtime instance/version/SHA;
- freshness TTL;
- explicit stale flag.

Live Diagnostics remains authoritative.

### 6.4 long-process orchestration

Preserved 1.x candidate branch:

`feature/1.x-managed-process-task-wait`

Candidate work includes:

- Runtime-local managed-process wait in Persistent Tasks;
- Worker-style long build/render flows;
- avoiding model polling;
- background/headless browser defaults where appropriate.

This should be evaluated as product/reliability work, not retrofitted into 1.0.

### 6.5 resource scheduling

Future priority/preemption is optional and evidence-gated.

If added:

```text
request revocation
→ current holder observes cancellation
→ holder closes safely
→ holder releases its own lease
→ next owner acquires
```

Never force-release a live owner's resource.

## 7. Later 1.x candidates

Only after evidence from real consumers:

### Run / Handoff Receipt

Compact run truth:

- status;
- artifacts;
- verification;
- approvals;
- remediation;
- health;
- provenance.

Especially useful for OWL Worker.

### Stage / ArtifactRef contract

Formalize durable task assets and provenance when both Worker and Computer MCP need the same semantics.

### EventSource / Watcher contract

Normalize external events into durable Task/Schedule wakeups.

Examples:

- file changed;
- email arrived;
- CI completed;
- app state changed;
- webhook;
- message arrived.

Do not embed infinite polling loops in providers.

### provider selection/fallback policy

Only if real multi-provider use requires it.

Must remain explicit and auditable. Consequential actions may never silently change ExecutionTarget.

## 8. What is NOT a 1.x goal by default

The following remain outside the normal 1.x budget unless product evidence changes the architecture decision:

- a second general-purpose Planner inside Runtime;
- autonomous kernel source modification;
- automatic Skill creation from one successful trace;
- enterprise billing/control plane;
- Kubernetes orchestration as a Runtime concern;
- full remote fleet management;
- speculative memory expansion;
- model-guessed side-effect recovery;
- product-specific business routing in the kernel.

Full production sandbox and federated/remote Runtime should be treated as major architecture work and are natural 2.0 candidates unless they can be added without violating 1.x contracts.

## 9. Consumer coordination

### Computer MCP

Does **not** need to wait for 1.1.

It should:

- keep its stable production release independent;
- consume RuntimeClient incrementally in development;
- use explicit backend selection;
- preserve stable macOS helper/runtime application identity;
- send generic Runtime gaps back as contract requests;
- not copy Runtime Scheduler, ownership, verification or recovery logic.

Transport instability belongs primarily to Computer MCP/tunnel, but Runtime must remain reconnect-safe.

### OWL Worker

Does **not** need to wait for 1.1.

It should build product behavior now against the frozen 1.0 RuntimeClient:

- Create Worker;
- Test Run;
- Confirm/Activate;
- Schedule;
- Run History;
- Approval;
- Health / Needs Attention.

If a missing capability is product-specific, Worker owns it. If both Worker and Computer MCP independently need the same execution invariant, that is strong evidence for Runtime 1.x.

## 10. Evolution rule

The permanent loop is:

```text
real Computer MCP / Worker failure
        ↓
evidence
        ↓
is it a generic execution invariant?
        ↓
yes
        ↓
smallest possible Runtime contract
        ↓
conformance test
        ↓
dogfood
        ↓
promotion in next allowed minor
```

Owl Lab remains the architecture research source. Runtime absorbs proven invariants, not experimental feature volume.
